## Claude compatibility requirements
- **Manifest resolution hierarchy**: Claude enumerates `.claude/agents/*.md`, `~/.claude/agents/*.md`, plugin `agents/`, and optional `--agents` JSON, resolving conflicts with priority project > CLI override > user > plugin. Agents can also ship with plugins.
- **Manifest schema & prompt body**: Each Markdown file starts with YAML frontmatter containing `name`, `description`, optional `model`, `tools`, `permissionMode`, `skills`, and `hooks` (PreToolUse/PostToolUse/Stop). The body becomes the system prompt for that subagent.
- **Delegation & built-ins**: Claude automatically delegates tasks whose natural language matches a subagent description and also respects explicit "Use the X agent..." instructions. Three built-ins (General-purpose, Plan, Explore) have fixed models, tool scopes, and sandbox guarantees; custom agents should coexist with them.
- **Tool & permission scoping**: Tool access is inherited from the parent session only when `tools` is omitted; otherwise the list is authoritative. `permissionMode` lets each agent change how aggressively it asks for approvals (default/acceptEdits/dontAsk/bypassPermissions/plan/ignore). `Task(AgentName)` rules can selectively disable agents.
- **Management & overrides**: The `/agents` surface and manual file edits both support CRUD operations. CLI `--agents` JSON makes ephemeral agents available without touching the filesystem.
- **Lifecycle contracts**: Subagents receive isolated context windows, emit `agentId` identifiers for resumes, can be chained, and are expected to persist transcripts (e.g., `agent-{id}.jsonl`). Hooks fire on tool boundaries to enforce policy.

## Current Codex capabilities
- **Instruction ingest vs manifest loader**: Codex still hydrates `AGENTS.md` via `codex-rs/core/src/project_doc.rs:1-170` for legacy instruction stacks, but the new `codex-subagent::FsManifestLoader` + `codex agents list` plumbing now parses `.claude/agents` Markdown/YAML/JSON manifests and CLI overrides so we can populate `AgentManifest`s alongside the existing instruction concatenation flow.
- **CLI surfaces**: `codex-rs/cli/src/main.rs:1-170` now exposes `codex agents list`, `codex agents resume-status`, and the new override flags (`--cli-manifest`, `--cli-manifest-file`, `--plugin`). `codex exec`/daemon parse those flags in `codex-rs/exec/src/cli.rs:95-110` and `codex-rs/exec/src/lib.rs:116-275`, convert them into `SubagentDiscoveryOverrides`, and stash them in `SessionConfiguration` so manifests can be listed, validated, or injected without touching the filesystem—mirroring Claude’s `/agents` UX.
- **Built-in personas**: `codex-subagent/src/builtins.rs` now ships `builtin-general-purpose`, `builtin-plan`, `builtin-explore`, and `builtin-review` manifests (`AgentKind::BuiltIn`). `Session::activate_subagent` hydrates them just like user manifests, `session_source_for_manifest` (`codex-rs/core/src/agent/runtime.rs:205-235`) maps them onto `SessionSource::SubAgent(SubAgentSource::{GeneralPurpose,Plan,Explore,Review})`, and both the CLI and TUI surfaces now highlight them explicitly (see `codex-rs/cli/src/agents_cmd.rs` for the `Claude built-in personas are always available` banner plus `codex --use-subagent builtin-*` hints).
- **Session metadata & variants**: `codex-rs/protocol/src/protocol.rs:1254-1286` now exposes typed `SubAgentSource::{Review,Compact,GeneralPurpose,Plan,Explore,Other(String)}` plus `SessionSource::SubAgent(...)`. Runtime activation (`codex-rs/core/src/agent/runtime.rs`) stamps these variants into lifecycle events, transport headers, and transcript indices so downstream tooling can differentiate built-ins from custom IDs.
- **Transport headers satisfied**: `ModelClient` injects `x-openai-subagent` whenever the session source is a subagent (`codex-rs/core/src/client.rs:372-400`), and the Responses/Chat requests mirror that via `subagent_header` helpers (`codex-rs/codex-api/src/requests/headers.rs:1-27`, `codex-rs/codex-api/src/requests/responses.rs:120-165`). The API side of the Claude contract is therefore partially ready.
- **Session-scoped approvals & tooling**: Tool approvals, sandbox decisions, skills managers, and MCP connections all live inside `SessionServices` (`codex-rs/core/src/state/service.rs:1-40`) and the `ToolOrchestrator` (`codex-rs/core/src/tools/orchestrator.rs:1-140`). There is no notion of per-agent tool allow-lists, permission modes, or hook callbacks; every delegate inherits the parent approval policy.
- **Docs & planning**: `docs/claude-subagent-plan.json` and `docs/claude-subagent-audit.md` capture desired milestones and highlight existing x-openai-subagent plumbing, but there is no implementation in any crate.
- **Transcripts & resume tokens**: Each activated agent now streams its own JSONL transcript under `~/.codex/subagents/<agent_id>/runs/<run_id>/`, writes a `resume.token`, and exposes it via `codex agents resume-status`. The CLI (`codex exec resume … --use-subagent <id> --agent-resume-token[-file]`) and daemon both pass the token through `SubagentOverride::Activate` so Codex can reload transcripts before re-activating an agent.

## Manifest ingestion (gap closed)
- **Discovery order + overrides**: `codex-subagent::default_discovery_targets` seeds each refresh with project `.claude/agents` plus user `~/.claude/agents`. When CLI/daemon callers provide overrides, `codex-subagent::build_discovery_targets` merges inline `--cli-manifest` JSON, `--cli-manifest-file` payloads, and `--plugin id=path` directories ahead of user/plugin scopes so the runtime and `codex agents list` both honor Claude’s priority (project > CLI > user > plugin). `AgentRegistry::refresh_with_telemetry` (`codex-rs/core/src/codex.rs:3535-3584`) still dedupes by id, and any skipped manifests produce `LoaderIssue`s that retain the winning scope for diagnostics.
- **Manifest schema + formats**: The shared `AgentManifest` schema in `codex-rs/codex-subagent/src/manifest.rs` covers every Claude field (`name`, `description`, optional `model`, `tools`, `permissionMode`, `skills`, `hooks`, `triggers`, plus the Markdown body). `FsManifestLoader` accepts Markdown with YAML front matter, standalone `.yaml`, `.yml`, `.json`, and CLI-provided JSON blobs, computes content digests, and validates each manifest via `validate_manifest` before handing it to the registry/runtime.
- **Validation surfacing**: CLI users can run `codex agents list --json` (implemented in `codex-rs/cli/src/agents_cmd.rs`) to inspect the merged manifest set plus any validation/de-dupe issues. The command renders `RefreshIssue`s that include the original file path, the `DiscoveryScope` label (project, cli, user, plugin), and the human-readable validation error so broken manifests can be fixed without digging through logs.
- **Telemetry + tests prove parity**: `init_agent_registry` logs every refresh through `codex.subagent_registry_refresh`, which now records CLI and plugin scope counts alongside project/user totals. `codex-rs/core/tests/suite/subagents.rs::subagent_discovery_overrides_emit_manifest_digests` asserts inline and plugin overrides survive activation with matching digests, and `codex-rs/cli/tests/agents_list.rs` locks the same ordering/issue summaries for the listing surface the TUI consumes.

## Runtime activation (gap closed)
- **Session caching path**: `init_agent_registry` (`codex-rs/core/src/codex.rs:3249-3289`) loads manifests up front, and `SessionServices::set_active_subagent`/`active_subagent` (`codex-rs/core/src/state/service.rs:24-105`) cache the `AgentRuntimeProfile` together with cloned approval policies, tool allow-lists, and hook sets so each turn can reference a stable snapshot without re-locking the registry.
- **Per-turn overrides respected**: `Session::activate_subagent` (`codex-rs/core/src/codex.rs:632-704`) builds an `ActivationContext` from the parent session, hydrates `AgentRuntimeProfile`, and stores it inside `ActiveSubagentRuntime`. `apply_active_subagent_overrides` (`codex-rs/core/src/codex.rs:709-742`) then patches the per-turn `SessionConfiguration` (model + approval policy), while `TurnContext::allowed_tool_names` and `TurnContext::hook_set` expose those cached slices downstream.
- **Tool gating and hooks**: `ToolScopeFilter::filter` (`codex-rs/core/src/agent/runtime.rs:115-134`) now intersects manifest allow-lists with the actual tool inventory, ensuring stale names never reach the router. `ToolRouter::from_config` (`codex-rs/core/src/tools/router.rs:27-73`) clamps specs and dispatch gating to that list, and `ToolOrchestrator::run` (`codex-rs/core/src/tools/orchestrator.rs:36-190`) wraps every call with manifest-defined pre/post/stop hooks via `codex-rs/core/src/subagents/hooks.rs`, matching the `docs/subagents/architecture.md#runtime--flow` contract.
- **Lifecycle telemetry**: `SubagentOverride::Activate` and `clear_active_subagent_with_hooks` (`codex-rs/core/src/codex.rs:2026-2185`) guarantee that `SubagentLifecycle` `Stopped` events fire before the next activation, and `emit_subagent_lifecycle_event` (`codex-rs/core/src/codex.rs:2091-2134`) now includes the manifest digest, effective approval policy, sandbox policy, and rollout/resume token in both the client event and OTEL trace.
- **Manifest refresh telemetry**: every code path now funnels through `AgentRegistry::refresh_with_telemetry`, which emits the `codex.subagent_registry_refresh` span plus per-issue `codex.subagent_manifest_issue` rows. The CLI companion (`codex.agents_list_invocation`) mirrors the same counts for `codex agents list --json`, so reviewers can line up manual inspections with runtime refreshes.
- **CLI/TUI breadcrumbs**: `codex exec --use-subagent …` and the TUI `:use-agent` slash command emit `codex.subagent_client_switch` events recording the session id, origin surface (`exec_flag`/`slash_command`), action (`activate`/`clear`), agent id, and status. These breadcrumbs surround the lifecycle telemetry so operators can see who requested a switch, whether it succeeded, and which manifest was involved even if the runtime never fully activated.
- **Tests covering the pipeline**: `codex-rs/core/src/agent/runtime.rs` ships `permission_and_scope_overrides_survive_activation` to exercise `PermissionResolver` + `ToolScopeFilter`. `codex-rs/core/tests/suite/subagents.rs` verifies tool gating, hook execution, lifecycle metadata (`subagent_lifecycle_events_include_metadata`), header propagation, and switching semantics (`subagent_switch_emits_stop_before_next_activation`), proving manifests drive the registry → activation → router → telemetry flow end to end.

## Gaps & risks
1. **Manifest ingestion (closed)**: The loader + registry stack described above now covers discovery, schema validation, and CLI surfacing, so the remaining risks focus on runtime plumbing and UX.
2. **Runtime discovery coverage (resolved)**: `SessionConfiguration::subagent_discovery_overrides` now carries the CLI/daemon `--cli-manifest`, `--cli-manifest-file`, and `--plugin` inputs all the way to `init_agent_registry`, so runtime refreshes see the same priority ordering as `codex agents list`. Scope counts for project/CLI/user/plugin show up in both `codex.subagent_registry_refresh` and `codex.agents_list_invocation`, and `codex-rs/core/tests/suite/subagents.rs::subagent_discovery_overrides_emit_manifest_digests` keeps the parity under test.
3. **Built-in agent parity (resolved)**: `SubagentLifecycleEvent` now embeds the `SessionSource::SubAgent(SubAgentSource::{GeneralPurpose,Plan,Explore,Review})` payload, and `codex-rs/core/tests/suite/subagents.rs::built_in_subagents_activate_without_manifests` asserts the activated/stopped lifecycle rows, transcript directories (`~/.codex/subagents/builtin-*`), and resume tokens for every built-in without requiring manifests. The CLI banners (`codex agents list`) plus TUI headers call out the `codex --use-subagent builtin-*` / `:use-agent builtin-*` entry points and the `codex agents resume-status` check, so reviewers can activate, resume, and inspect the Claude-style personas out of the box.
4. **UX/CLI gap (resolved)**: The new `codex agents list` command prints provider/priority/validation metadata (matching Claude’s `/agents` view), `codex exec --use-subagent ...` prints the active agent/model/tool scope before streaming, and the TUI now has an always-visible header showing which agent is active plus a reminder that `:use-agent <id>` or `--use-subagent <id>` can switch contexts.
5. **Observability & persistence (resolved)**: Each activation now streams to `~/.codex/subagents/<agent_id>/runs/<run_id>/agent-<run_id>.jsonl`, drops a run-scoped `resume.token` + `index.json`, updates the agent-level `index.json`, and surfaces everything via `codex agents resume-status` (human + JSON). Long-term retention policies and concurrency (multiple simultaneous runs per agent) still need tuning so the on-disk layout doesn’t grow without bound.
6. **Watch-driven refreshes (resolved)**: `codex-core::agent::AgentRegistryWatch` now owns the loader’s `LoaderWatch`, debounces filesystem/plugin events (~300 ms), reruns `refresh_with_telemetry(…, RefreshInvocation::Watch)`, and emits structured logging/telemetry plus `RegistryEvent`s for CLI/TUI consumers. Follow-up work moves the CLI/TUI to opt into this shared handle, but the registry side can already surface scope labels, refresh counts, and errors as events.

## Open questions
- How should Claude's `permissionMode` map onto Codex's `AskForApproval` enum and execpolicy overrides - does each agent clone the session and override approval fields, or do we introduce a per-agent approval cache layered on `SessionServices`?
- Should built-in agents (Plan, Explore, General-purpose) be represented as manifests checked into the repo, hard-coded tasks similar to `ReviewTask`, or a hybrid with generated manifests to keep parity with Claude semantics?
- How will per-agent tool allow-lists interact with MCP tool registration and the `ToolOrchestrator`; do we need to add filtering before presenting tools to the model, or should approval prompts encode the restriction?
- What identifier/resume mechanism maps best to Claude's `agentId` contract - do we keep a single rolling transcript per agent, or retain multiple run directories and expire them over time?
